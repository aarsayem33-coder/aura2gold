# Public Market Feed — Implementation Plan

**Status:** Not started. Scope not yet fixed — the field allowlist (Phase 0) must be agreed before any code is written.
**Created:** 2026-08-06
**Goal:** Let external viewers see selected market information from the Aura system, read-only, without exposing the trading machine or any account data.

---

## 1. Problem

All market data originates from the MT5 terminal on the local PC and lands in the local MySQL
(`aura_gold_alerts`, migrated 2026-08-06). Nothing is reachable from outside. We want a public
page showing a chosen subset of that information, updated continuously.

## 2. Non-negotiable constraints

These come from what the system actually contains, not from theory.

### 2.1 Never expose the backend directly

The backend serves order-execution routes on the same Express app as the read endpoints:

- `POST /api/auto-trade/:id/approve`
- `POST /api/mt5/trade-bridge`
- `POST /api/ict-predictions/:id/place-order`
- `POST /api/setup-forecasts/:id/place-order`

A tunnel (ngrok, Cloudflare Tunnel, port-forward) puts **real order placement on the public
internet**. One auth misconfiguration is a live trade on a funded account. Read-only viewing
must never share a process, port, or hostname with trade control.

**Decision: outbound push only. No inbound path to the PC, ever.**

### 2.2 Allowlist, never denylist

A single `/api/mt5/status` response (35 top-level keys) already contains:

```
account          → 1514176421
broker           → FTMO Global Markets Ltd
accountSnapshot  → balance, equity, margin
processId, ingestUrl, heartbeatUrl, snapshotUrl, candlesUrl, tradesUrl
```

With a denylist, any field added to a payload later is published automatically. The publisher
must name every field it emits and drop everything else by default.

### 2.3 Staleness must be visible

The feed depends on the PC being awake with MT5 running. Sleep, reboot, or a dropped EA means
a frozen feed. A viewer reading a stale price as live is the worst failure mode here, worse
than showing nothing. Every payload carries `generatedAt`; the UI degrades loudly past a
threshold.

## 3. Open questions (blockers for Phase 0)

1. **Which fields?** Tiering to decide against:
   - *Derived/safe* — HTF bias, trend/regime, key liquidity levels (PDH/PDL, session H/L), volatility state, session clock
   - *Medium* — strategy verdicts, setup scores, forecast ETAs, AI chart-read summaries
   - *Sensitive* — entry/SL/TP tickets, live P&L, win rates
   - *Never* — account number, balance, equity, lot sizes, broker/terminal identity, internal URLs
2. **Broker terms** — redistributing broker price data publicly may breach the FTMO/broker
   agreement. Derived/aggregated values are generally safer than raw candles. Needs checking
   before any raw OHLC is published.
3. **Regulatory** — publishing entry/SL/TP reads as investment advice in many jurisdictions.
   Decide whether this is *market information* or *trade recommendations*; the latter carries
   obligations.
4. **Audience** — fully public, or link/token-gated for a known group? Changes hosting and auth.
5. **Freshness target** — 30–60 s push is cheap and sufficient for context. Sub-second needs
   WebSockets and real hosting.

## 4. Architecture

```
Your PC                                  Hosted (public)
┌──────────────────────────┐             ┌────────────────────────┐
│ backend :5000            │   HTTPS     │ public API (read-only) │
│ local MySQL              │  ────────▶  │ snapshot store         │ ◀── viewers
│ publisher (allowlist)    │  outbound   │ static UI              │
└──────────────────────────┘   only      └────────────────────────┘
```

- **Publisher** — a module in the local backend. Reads local MySQL / in-memory state, projects
  it through an explicit allowlist, POSTs a JSON snapshot to the hosted endpoint on an
  interval. Its only job is projection + transport; no business logic.
- **Hosted API** — accepts authenticated writes from the publisher, serves unauthenticated
  reads. Stores the latest snapshot (plus optional short history).
- **Public UI** — static page reading the hosted API. No connection to the PC.

### Hosting options

| Option | Notes |
|---|---|
| Existing Hostinger MariaDB | Already paid for, retained for rollback. Tight limits: `max_connections_per_hour=500`, `wait_timeout=20`. One persistent publisher connection at 30–60 s fits. |
| Cheap VPS | Full control, simplest mental model, ~$5/mo. |
| Serverless KV / object storage | Cheapest and simplest for a single latest-snapshot document. Good default if no history is needed. |

## 5. Phases

### Phase 0 — Fix the scope *(blocker)*
- Agree the field-by-field allowlist against the tiers in §3.1.
- Resolve broker-terms and regulatory questions.
- Choose audience and freshness target.
- **Output:** a reviewed `publicFeedFields.js` allowlist spec. No code until this is signed off.

### Phase 1 — Publisher (local, no hosting yet)
- `backend/publicFeed.js`: build snapshot from the allowlist; pure function, unit-testable.
- Test asserting the projection contains **only** allowlisted keys, with a deliberate case
  proving a newly added sensitive field is dropped by default.
- Write snapshot to a local file / debug endpoint for inspection.
- **Exit:** snapshot is byte-inspectable and provably free of account data.

### Phase 2 — Hosted receiver
- Minimal API: `POST /ingest` (API key), `GET /snapshot` (public).
- Key in env, never committed. Reject oversized/malformed payloads.
- Rate-limit reads; cache aggressively (data changes at most once per interval).

### Phase 3 — Transport
- Publisher pushes on interval; retry with backoff; never block or slow the trading path.
- Failures log and drop — a publishing outage must never affect signals or execution.
- One persistent connection if targeting the Hostinger DB (respect the 500/hr cap).

### Phase 4 — Public UI
- Static page: the agreed market information, plus a prominent `last updated` and a loud
  stale banner past threshold.
- No account, P&L, or execution surfaces.

### Phase 5 — Hardening
- Verify from a clean network that no PC-hosted route is reachable.
- Confirm published payload against the allowlist one final time.
- Add a kill switch (`PUBLIC_FEED_ENABLED=0`) that stops publishing immediately.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Account data leaks | Strict allowlist + a test that fails when unknown keys appear |
| Trading API exposed | Outbound-only; no tunnel; separate host and process |
| Stale data read as live | `generatedAt` in every payload; loud UI degradation |
| Broker ToS breach | Resolve in Phase 0; prefer derived values over raw candles |
| Publisher harms trading | Fully isolated; failures logged and dropped; kill switch |
| Hosted DB quota | Single persistent connection; interval push, not per-event |

## 7. Explicitly out of scope

- Any inbound access to the local machine
- Any write/control path from the public side
- Publishing account, balance, equity, lot sizes, or broker identity
- Changes to signal, strategy, auto-trade, or AI logic — the publisher only *reads*
